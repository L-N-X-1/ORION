PROJECT OVERVIEW
--------------------------------------------------------------------------------
ORION ("Operational RAN Intelligence & Optimization Network") is a home-lab
autonomous NOC for a simulated 5G RAN. Internal code/comments still call it
AURA-NET (pre-rename codename) — this appears in docstrings, FastAPI app
titles, and Kafka topic names (aura.event.v1, aura.kpi.v1); it is the same
project as "ORION" in the README/branding, not a separate system.

Closed loop (logically — see SEPARATION note below for the current physical
repo state): a SimPy digital twin (digital-twin/) simulates a 12-cell gNodeB
grid driven by real Milan mobile-traffic CSV data, emitting KPIs and
threshold-crossing events onto Kafka. A 7-node LangGraph pipeline
(agentic-ai/services/ai-agent) consumes those events and runs:
  Triage -> Root Cause -> Planner -> Safety -> [Human Approval] -> Executor -> Verifier
Deterministic policy rules (agentic-ai/services/ai-agent/safety/policy_engine.py) gate
every action; an LLM (Ollama, local, default model llama3.3) enriches
narratives and makes bounded choices at each stage but never bypasses the
rules. The Executor calls agentic-ai/services/actuator to apply changes back onto the
digital twin; the Verifier compares before/after KPIs and can trigger
automatic rollback. A React dashboard (agentic-ai/ui/dashboard/react-app) gives an
operator visibility + manual controls + a pending-approvals queue.

There are TWO unrelated React apps in this repo — do not conflate them:
  agentic-ai/ui/dashboard/react-app  = the agent pipeline's 4-page dashboard
                                       (see FRONTEND section)
  digital-twin/ui                    = the Twin Console, the digital twin's own
                                       9-page operator UI, added 2026-09-05
                                       (see TWIN CONSOLE section)
They share no code, no build, no container and no port. The Twin Console talks
only to digital-twin:8001 and embeds Grafana; it does not reach agentic-ai.

SEPARATION — digital-twin/ and agentic-ai/ are two fully independent repos-
in-one-repo, each with its own docker-compose.yml/.env.example/Makefile, and
they are NOT networked together:
  Repo root now contains exactly two source directories — digital-twin/ and
  agentic-ai/ — plus loose root files (README.md, LICENSE, PROJECT_MAP.txt,
  tree.txt, .gitignore). Everything that used to live at root or under
  services/ was sorted into one of the two:
    digital-twin/  = the twin app + its OWN zookeeper/kafka/influxdb/grafana
                      (data/csv, data/kafka, grafana/provisioning all moved
                      inside it — data/timeseries/influxdb/init.sh was
                      removed in a later pass, see CONFIG section below)
    agentic-ai/     = services/{collector,actuator,api-gateway,ai-agent} +
                      ui/ (react dashboard + nginx) + its OWN
                      zookeeper/kafka/redis/postgres/prometheus + tests/ +
                      docs/ (data/kafka [duplicated into both stacks — see
                      below], data/timeseries/postgres, infra/prometheus.yml
                      and the (now auto-loading) docker-compose.override.yml)
  Both stacks got their OWN Kafka+Zookeeper (data/kafka's aura.*.v1 schemas
  were duplicated into digital-twin/data/kafka AND agentic-ai/data/kafka;
  topics.sh was duplicated too but digital-twin's copy was later deleted —
  it was never mounted or executed anywhere, since KAFKA_AUTO_CREATE_TOPICS
  _ENABLE=true already creates both topics on first publish. agentic-ai's
  copy is unchanged) so each can run standalone without the other, on
  distinct host ports (digital-twin's Kafka is published on 9093, not 9092,
  to avoid a collision if both stacks run at once). InfluxDB+Grafana moved
  to digital-twin only (nothing in agentic-ai reads/writes InfluxDB —
  collector's query_metrics.py is still a stub); Postgres+Redis+Prometheus
  stayed with agentic-ai only (actuator/postgres, ai-agent/redis).

  What this means in practice: agentic-ai/services/ai-agent's TWIN_URL,
  agentic-ai/ui/dashboard/react-app's TWIN_TARGET, agentic-ai's nginx
  /api/twin/ + /grafana/ routes (now commented out — nginx fails to start
  with a dangling static proxy_pass target), and agentic-ai/infra/
  prometheus.yml's digital-twin scrape job (now removed) all point at a
  "digital-twin" hostname that does not exist on agentic-ai's docker
  network. This is intentional and NOT yet fixed — the user explicitly
  deferred re-connecting the two stacks ("we will manage the correlation
  between them later"). Whoever does that later will need to either put
  both stacks' containers on one shared external docker network, or point
  agentic-ai's env vars at digital-twin's host-published port 8001 (e.g.
  via host.docker.internal), and un-comment the nginx blocks +
  re-add the prometheus job.

  Before this pass, the twin briefly lived at services/digital-twin/ (moved
  to top-level digital-twin/ in an earlier step) with everything else still
  under one shared services/ + one root docker-compose.yml — that
  intermediate state no longer exists; this SEPARATION note supersedes it.

Two agentic-ai services are effectively stubs: agentic-ai/services/api-gateway
(only /health implemented — no auth/RBAC/routing exists anywhere in the
stack) and most of agentic-ai/services/collector (only /health implemented;
http/mqtt/kafka ingestors and query_metrics are all 4-line TODO placeholders
— nothing in agentic-ai currently reads or writes InfluxDB as a result,
which is also why InfluxDB was not duplicated into the agentic-ai stack).

ROUTING — how a browser request actually reaches a backend service
================================================================================
TWO SEPARATE ROUTING SETUPS, one per stack. The Twin Console's is described
first because it is the simpler and newer of the two; the agentic-ai dashboard's
follows.

--- digital-twin/ui (Twin Console) — host 8080 ---
The browser only ever talks same-origin. Both dev and container use the same
paths, so nothing in the app code branches on environment:

  DEV (vite dev server, `npm run dev` / `make ui-dev`, port 5173):
      /api/twin/*   -> TWIN_TARGET    (default localhost:8001), ws:true
      /grafana/*    -> GRAFANA_TARGET (default localhost:3001)

  DOCKER / PROD (digital-twin/ui/nginx.conf, container port 80 -> host 8080):
      location /            -> try_files, SPA fallback to /index.html
      location /api/twin/   -> digital-twin:8001/  (REST *and* the
                                /ws/telemetry WebSocket — the Upgrade /
                                Connection headers plus the http-scope
                                `map $http_upgrade $connection_upgrade` are
                                what make the upgrade survive the proxy)
      location /grafana/    -> grafana:3000  (JSON API only, see below)
      location = /healthz   -> 200, compose healthcheck target

  Grafana is the one thing NOT reached same-origin: the d-solo/kiosk iframes
  load from Grafana's own published origin (default <host>:3001, overridable
  via the VITE_GRAFANA_URL build arg or a per-browser localStorage setting).
  Only the Analytics page's dashboard-panel-list FETCH goes through the
  /grafana/ nginx proxy, because Grafana emits no CORS headers and the
  browser blocks that call cross-origin. Doing it this way avoids setting
  GF_SERVER_ROOT_URL + GF_SERVER_SERVE_FROM_SUB_PATH, which would have moved
  Grafana off its own root and broken direct access on :3001.

  GOTCHA (already fixed, do not reintroduce): the compose healthcheck must
  use http://127.0.0.1/healthz, not http://localhost/healthz. nginx binds
  IPv4 only; inside the container `localhost` resolves to ::1 first and the
  connection is refused, so the container serves traffic fine while reporting
  unhealthy.

--- agentic-ai/ui/dashboard/react-app — host 80 via its own nginx ---
The dashboard NEVER calls TWIN_TARGET/ACT_TARGET/AGENT_TARGET directly from
the browser. Those docker-compose env vars are consumed server-side:

  DEV (vite dev server, `npm run dev`):
    vite.config.ts reads TWIN_TARGET/ACT_TARGET/AGENT_TARGET (falling back to
    localhost:8001/8003/8004) and proxies:
      /api/twin/*  -> TWIN_TARGET/*
      /api/act/*   -> ACT_TARGET/*
      /api/agent/* -> AGENT_TARGET/*

  DOCKER / PROD (agentic-ai/ui/nginx/nginx.conf, port 80) — CURRENT STATE,
  post-separation:
      location /              -> react-app:3000            (the SPA itself)
      location /grafana/      -> COMMENTED OUT — grafana now lives in the
                                  digital-twin stack, not on this network
      location /api/          -> api-gateway:8000/          (generic catch-all)
      location /api/twin/     -> COMMENTED OUT — same reason as /grafana/;
                                  a live static proxy_pass to a hostname that
                                  doesn't resolve would stop nginx starting,
                                  so it's disabled rather than left dangling
      location /api/act/      -> actuator:8003/             (more specific, wins)
      location /api/agent/    -> ai-agent:8003/              (more specific, wins;
                                  8003 is the container's INTERNAL port — see
                                  docker-compose "8004:8003" port mapping)

  Net effect: nginx's more-specific /api/act|agent/ locations shadow the
  generic /api/ -> api-gateway location for every request the dashboard
  actually makes. The api-gateway container receives essentially no live
  traffic. This matches agentic-ai/services/api-gateway being an unimplemented stub
  (see API GATEWAY section above) — the routing config was future-proofed for
  a gateway that was never finished, not left in place by mistake.
  /api/twin/ and /grafana/ being disabled is a SEPARATE, newer issue — see
  the SEPARATION note in PROJECT OVERVIEW — and needs re-enabling once
  digital-twin and agentic-ai are networked together.
